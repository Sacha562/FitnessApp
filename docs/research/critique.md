## GAPS
- No single module owns time-zone, day boundary and week boundary handling (ISO Mon-Sun, Europe/Amsterdam, DST end 2026-10-25), even though five modules use 'week'. | WHY: Planner ISO week vs challenge completion-driven block week vs rolling 7-d windows: if each module rolls its own, DST shifts or a missed tick produce diverging week assignments. | FILL: A Clock/Calendar utility in :algo: Instant for elapsed hours, LocalDate in the user's zone for day/week, explicit isoWeek(), and an injected clock. Golden tests spanning 2026-10-25.
- The challenge block week and the general mesocycle week diverge when a challenge week repeats (missed week) or an extra deload is inserted. | WHY: The general deload sync and ROT-1's anchor locks assume a 5-week calendar cadence. | FILL: While a challenge is active, the general mesocycle index = challenge block.index/week (read from the contract). Otherwise it is the calendar 5-week cadence.
- The data model lacks fields the algorithms consume: per-set flags (gripSlipBeforeLast, jerky, torsoRotation, hipRotation), seconds-in-reserve for holds (HOLD-1 s_res), finger-assist ordinal, top-hold rounds/attempts, eccentric target vs actual seconds, per-set F_i/n_fresh, machine_id/station on set, mode (assisted/bodyweight/weighted) on set, dumbbell per-hand vs total convention. | WHY: Challenge rules (valid(), progression guards) and SSE-1/HOLD-1 can't run or be replayed without them. | FILL: set_logs: flags text[], hold_reserve_s, assist_ordinal int, attempt_index, round_index, ecc_s_target/actual, load_mode, equipment_id, implement_count (1/2) and load_per_implement. Derived engine fields go in recommendation trace / exercise_model_state, not in facts.
- Test-day metrics need validity and protocol versioning (validForGate, protocol id, measured vs calculated 1RM, 'old protocol, not comparable'). | WHY: Phase gates and stall rules compare tests. The artifact already has invalid tests (2026-09-19 3RM-only, 2026-09-29 hang). | FILL: metric_observations: valid_for_gate bool, protocol_code, derivation (measured|calculated:<method>), enrollment_id, test_session_id. Import the three historical tests with these flags.
- Challenge home habits (daily two-arm hang 17:15, one-arm plank Tue/Thu 17:30) have no storage or completion model and no notification spec. | WHY: The plank progression rule fires on habit.completed. The daily hang is skipped on A-days and halved on deload. Todoist duplication is possible. | FILL: workout_sessions.kind ∈ {gym, home, test}, so habits are tiny home sessions. Reminders via WorkManager/AlarmManager. Ask whether Todoist tasks stay.
- Free or unplanned sessions (user trains without a recommendation, or does a challenge session on a different day than the calendar) have no defined flow. | WHY: Readiness, volume and the challenge week count must still be updated, and the calendar link is missing. | FILL: Start session → pick template (challenge slot A/B/C/TEST, family combo, or empty). The calendar link is attached post hoc (±3 h, same day). Challenge session.completed fires on the template slot, not on the calendar.
- No rule for when the calendar contradicts the challenge state (e.g. 'testdag' event Sun but needsCleanSession true → test postponed, while the calendar still shows the test). | WHY: The planner would treat Sunday as TEST and keep Saturday rest-blocked, and the user sees conflicting info. | FILL: Challenge state wins for slot type: a TEST event is re-typed to B (or flagged) and the user is prompted to rename or move the event (read-only v1), or the app does it when write-back is enabled.
- Calendar edge cases not covered: events spanning midnight, multiple gym events per day, events edited mid-session, declined/cancelled instances, recurring instance exceptions, calendar permission revoked, phone calendar sync lagging Google. | WHY: Wrong anchors give wrong protect windows and rest days. | FILL: Use the Instances table; local date = start date; dedupe within 120 min; ContentObserver re-plan; 'calendar unavailable' degraded mode (plan without anchors plus a banner).
- Offline edge cases: first login needs network; params/challenge definition versions not yet pulled; session spanning a params update; two devices; reinstall with a non-empty outbox; Free-plan project paused. | WHY: Determinism (params pinned per session) and data loss. | FILL: Bundle default params, catalog and the OAP definition in the APK as fallback. Pin params_version at session start. Block sign-out/reinstall while the outbox is non-empty. Sync-status chip. Monthly JSON export.
- Bodyweight handling is fragmented: S4 (last obs, 14-d stale), LOAD-1 LP (EWMA alpha 0.3), A5 (latest weigh-in), challenge (test-day weigh-in, threshold = ratio x BW). | WHY: BW changes shift assisted and weighted prescriptions and the OAP gate. | FILL: One BW(t) function: EWMA of weigh-ins for prescriptions; the raw test-day weigh-in for gates; a snapshot stored on every set and session; a prompt if >14 d stale.
- Eccentric-only, isometric and assisted-ordinal sets have no e1RM path. - Multiple users (friend 2x12, women legs-only) are a requirement example, but the defaults assume a young male (age/sex unused, f_bw male segments, maintain rules ≥60). Other chess accounts could log in. | WHY: Wrong defaults and data exposure. | FILL: profiles: sex/age optional with defaults that don't depend on them; per-user params; an RLS allowlist (fitness.allowed_users) if the user wants to restrict access.

## UNSUPPORTED
- Camargo et al. 2026 (+120% vs +20% volume, no hypertrophy difference): verified as a bioRxiv PREPRINT (via biolayne). app_benchmarks rates it 'strong' and uses it for the +20% cap. Downgrade to weak/preliminary.
- Coleman deload RCT is PeerJ 2024 (verified via Europe PMC); app_benchmarks cites 2023. The finding (1-week cessation: similar hypertrophy, slightly worse strength) is fine.
- ACSM 2026 Position Stand (Currier et al., MSSE 58(4):851-872) verified: ≥2 sessions/wk, ≥10 sets/wk for hypertrophy, 2-3 RIR enough, periodization not superior. It also says rest intervals (<1 vs >1 min) show no consistent impact, so lens claims that long rest is needed for hypertrophy are overstated. Treat rest defaults as performance/time trade-offs.
- Remmert et al. per-session PUOS (~11 fractional sets hypertrophy, ~2 direct for strength) is an unreviewed SportRxiv preprint. Used as a hard cap (CAP_S 10) and warning threshold in several lenses: keep it, but rate it weak.
- Planning's specific Bayes-factor figures for Pelland 2026 (2xlogBF ~10.8 / ~10.0) could not be verified in this pass. The direction (fractional counting fits best) is consistent across lenses.
- Marzagao 2026 (arXiv 2603.17495, single author, Fitbod logs) is cited for exercise-specific k. It is weak and scores consistency, not accuracy vs tested 1RMs.
- Personal k = 30.6 (+39.2 kg e1RM) comes from two points ~20 days apart (BW x18 on 30 Aug, 3RM +32.5 on 19 Sep). load_prescription's own rule requires ≤14-day windows, and the BW-reps point is >12 reps where RIR/rep accuracy is poor. Plausible but fragile. Present it as a range (+37..+42.8), not a correction.
- Several load_prescription citations are explicitly 'from memory' (Lasevicius 2018, Schoenfeld 2017 volume, Sanchez-Medina 2011). The APRE adjustment table is 'recalled'. Verify before encoding constants that cite them.
- Assisted machine offset 6.5 kg is the user's estimate ('6-7 kg'), back-fitted to match artifact numbers. It is not measured, and the machine's lever ratio (1.0) is assumed.
- OAP threshold 65% BW (+46 kg), neutral 70% and pronated 75% are coach heuristics (Kavadlo/Willoughby/StrongFirst forum). The grip-specific ratios are unsourced interpolations per the artifact itself.
- Fitbod 'more often +40-60% / less often -20-40%', 6-7 day full recovery; Gravl 7% second-exercise discount and ~10% cap; 'RP ignores joint pain': these come from marketing or third-party reviews, not code. Use them only as starting constants.
- Recovery time constants (tau 20-44 h), F_REF/cap values, run fatigue coefficients, isometric credit 0.5/0.25, novelty 1.5x, protect windows 24/30/48 h, tissue tau 48 h: all assumptions or extrapolations (Miller 2005 is collagen synthesis, not 'readiness'). Mark them tunable, never 'evidence-based'.
- tech_stack library versions (AGP 9.4.0, Gradle 9.6/9.8, Kotlin 2.4.20, Compose BOM 2026.09.00, Room 2.8.5, supabase-kt 3.8.0, Navigation3 1.2.0) are not independently verified here. Pin them only after checking Maven Central at scaffold time.
- tech_stack lists 'assistant' among the exposed schemas. The data_model live probe (PGRST106) shows only public, graphql_public.
- free-exercise-db entry count: 873 (ux) vs 876 (exercise_selection, fetched). Trivial, but use the fetched value.
- Planning's OAP committed volume (lats 25-30, biceps 15-17) and challenge_engine's (lats 22-26, biceps 22-25) are both derived from unvalidated coefficients. Neither is evidence, and the 'pull is covered' conclusion depends on them.

## RISKS
- Scope and complexity explosion: 8 lenses specify about 45 algorithms with 3-5 overlapping versions each. Building them all first means months before the user can log a set, and the constants are unvalidated anyway. => Consolidate to one module per concern (see contradictions). Phase delivery: the logger and the OAP challenge first, the general planner later. Every constant goes in params JSON with an evidence grade, so it can be tuned after usage.
- Elbow/tendon injury from the challenge plus general add-ons: supinated one-arm work, weighted negatives, the ungated -5 lb/week pin in A (+4.9%/wk one-arm load), and general curls or grip work in protect windows. => SafetyState evaluated first. One-tap pain report. Readiness elbow check before challenge sessions. Pin progression gated by default (opt-out). Grip/elbow-flexor tags forbidden in protect windows. No failure on high-risk lifts. App disclaimer.
- Model-dependent e1RM (+38 to +46.9 kg from the same 3RM) leads to misleading phase-gate progress and user expectations. => Gates use measured test values per a user-chosen method. Show an e1RM range with CI and the method label. Never silently switch the user's rule.
- Shared Supabase project (chess app, Free plan): config push, db push/repair, a mistaken PATCH of db_schema, a missing RLS/grant, an auth.users trigger, the 500 MB read-only cliff, no backups, pausing. => MCP apply_migration only, with the user reviewing each migration. The user changes Exposed schemas in the dashboard (append fitness). Composite FKs + RLS + no anon grants + advisors after each migration. Size guard. Local-first + exports. No triggers on auth.users.
- Data-entry friction in the gym (L/R x sets x RIR x flags x seconds) leads to incomplete logs, so rules evaluate on missing data and estimators drift. => One-tap RIR-as-log, prefilled loads, hands-free hold timer with correction, a tap budget ≤6 outside sets, logged untouched/skip rates, and conservative imputation (no increase on missing data).
- Hard-constraint conflict: under the artifact's literal gap rule, no extra gym day is possible. If the planner ignores this, the user gets contradictory advice. If it obeys, legs/push only fit as short add-ons. => The gap-rule scope is a challenge parameter decided by the user. The planner reads it from the contract. Golden test on the real week.
- Calendar parsing errors (Dutch titles, em dash, diacritics, shifting days, stale Todoist all-day events, renamed events) mis-type sessions, giving wrong prescriptions and windows. => Primary-calendar allowlist, all-day ignore, normalization, title patterns from the challenge definition, confirm when score <0.8, per-event override, classification log.
- Rest timer unreliability (exact alarm permission, Doze, OEM killers, FGS type requirements). => setAlarmClock + chronometer notification + health/specialUse FGS for the session, timestamp-based state, restore on restart, battery-optimization prompt, latency logging, on-device Doze test.
- Determinism/replay breaks (Math vs StrictMath, HashMap order, locale, clock in :algo, float vs decimal boundaries, JCS vs jsonb::text hashes). => :algo forbids android.*/clock/random imports (lint test). StrictMath. Canonical rounding grid. JCS client hashes only. Replay CLI golden tests in CI.
- Toolchain: no Android SDK, Java 25 only, user must accept SDK licenses and enable wireless debugging. A lost signing key forces reinstall and wipes unsynced data. => Daemon JVM pinned to Temurin 21, cmdline-tools installed with the user's consent, Roborazzi + adb screencap for visual checks, release keystore backed up, block reinstall while the outbox is non-empty.
- Overfitting personal constants (k, kappa, RIR bias) to sparse or fatigued data, then wrong loads. => Priors with shrinkage, minimum-sample gates (12 obs, RTF spread ≥3-4, 14-d windows), per-fit rate limits (±10%), review-approved params changes only.

## ARCHITECTURE
One pure, versioned Kotlin JVM module :algo (no android.*, no clock/random/IO; StrictMath; canonical rounding kg 0.01 / s 0.1; stable sorts with id tie-breaks) is called by :app (UI and services) and :sim (replay CLI). The entry point is Engine.run(EngineInput, Params, clock-injected now) → Output + DecisionTrace. Every call is snapshotted to fitness.recommendations as {module@version, ENGINE_VERSION, params_hash, catalog_version, challenge_def sha256, inputs_hash (RFC 8785 JCS + SHA-256), inputs, outputs, trace}. Params are pinned per session.

DATA LAYER: Room is the source of truth: facts (set_logs, session_events, metric_observations, wellness/pain, calendar classifications), config (prefs, goals, equipment, user_algo_params) and caches (exercise_model_state, challenge state). An outbox (append-only tables: ignore-duplicates; mutable tables: upsert + server LWW trigger) syncs to schema fitness. Pull uses a server_updated_at cursor with 120 s overlap. Bundled fallbacks: default params, the ~150-exercise catalog and the OAP definition.

PIPELINE (in order; precedence safety > challenge > user hard constraints > general):
L0 Normalize: Clock/Week (Europe/Amsterdam, ISO week, Instants). LoadModel (one LOAD fn: w_sys = f_bw*BW(t) + added - assistKg(pin, calib); loadable sets per equipment; nearest_loadable). BW(t) (EWMA for prescription, raw for gates). CalendarClassifier.v1 (CalendarContract Instances → typed anchors: challenge_session(slot), planned_gym(type), run(minutes, intensity), busy; challenge title patterns come from definitions).
L1 Safety: PainEvents + readiness check → SafetyState (joint flags, challenge injury mode, forbid tags). Evaluated first on every event.
L2 Challenge layer: event-sourced enrollment fold + FitExpr ECA rules (stage order safety < data < structural < progression; first-writer-wins + locks) → challenge state, materialized sessions (templates x phase x mode), and a ChallengeContract {reserved sessions, blocked days with scope, protectedWindows (hard/penalty), gap-rule scope, ownsMuscles, committed per-muscle/tissue dose (computed by SetCredit on materialized sets), add-on slots (TIME-1 capacity, allowed patterns, forbidden muscles/tags), deload/test week, block index for mesocycle sync}.
L3 Accounting/estimation: SetCredit.v1 (fractional volume, strength credit, fatigue and tissue dose; one RIR table; unilateral pair = 1). MuscleReadiness (muscle tau x kappa, tissue, systemic; runs as leg fatigue). RIRCAL-1 → RCM-1 (k) → SSE-1 (M, g, P) on dynamic sets only. FAT-1 within-session. HOLD-1 for holds. STALL-1 weekly.
L4 Targets: WeeklyTargets (goals, training age, mesocycle week from the contract or the 5-week cadence, ramp from the soreness x performance signal capped at +20%, DeloadPolicy, re-entry >21 d, challenge-covered muscles, MRV caps).
L5 Planning: WeeklyPlanner (exhaustive enumeration over free days x family combos x add-on options, under the contract's hard constraints; simulate with SessionDoseAllocator + readiness) → this week's recommended sessions and rest days. TodayRecommender = the same scorer for today (ranked options + reason chips via UI-01).
L6 Session build: ELIG-1 (bans, inventory, safety/contract tags, disliked-necessity gate) → SEL-1 beam search (pinned challenge block first; general/add-on block gets the time budget) → ORD-1 → TIME-1 trim (UI-02 tiers) → RX-1 per exercise (model / DOUBLE with rep ladder / RULE mode for challenge items, model in shadow) → WARMUP-1 → REST-1 timers → WarningEngine (merged W/R rules, tiered severity, UI-10 display policy, evidence_mode setting).
L7 In-session: each logged set → REASON-1 semantics → challenge inSessionRules → UI-06 trigger → AUTO-1 recompute (suggest/apply) → SUB-1 on occupied (reorder first) → rest timer (setAlarmClock + chronometer notification + FGS). Add/remove/skip are events.
L8 Post-session: SSE/RCM/RIRCAL/FAT updates; challenge session.completed rules; readiness update; replan week; snapshot + telemetry; sync.
Offline review loop: fitness_review views read engine-logged values (never re-derive e1RM in SQL). :sim replays logs under a candidate ENGINE_VERSION/params and diffs outputs. ModelTuner proposes params, and approved ones are written to user_algo_params with valid_from.
