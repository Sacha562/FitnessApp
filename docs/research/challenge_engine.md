# LENS challenge_engine

## SUMMARY
Challenges = data, not code. Recommend: (1) versioned JSON Challenge Definition (CDS v1) stored as immutable rows in Supabase (jsonb + pg_jsonschema check), authored/reviewed by Claude Code, cached on device; (2) tiny custom typed expression language FitExpr (infix strings -> AST, decimal math, units kg/lb/s, no loops, vectorized list ops + explicit all/any) instead of JSON-Logic/CEL/JS; (3) event-sourced enrollment (append-only events -> deterministic fold -> state + per-block snapshots), so any engine/definition version can be replayed by a JVM CLI for algorithm reviews; (4) ECA rule engine with staged single-pass snapshot semantics (safety > data > structural > progression), first-writer-wins + noIncrease locks, full audit row per firing; (5) completion-driven week/block advance (wger need_logs_to_advance pattern) which natively implements 'missed week = no make-up, same loads' and test postponement; (6) calendar matcher (normalized regex + location + duration scoring, max-weight matching, marker tag for app-written events); (7) integration contract: challenge reserves sessions, declares owned muscles, protected windows, add-on slots, and computed per-muscle coverage; general engine fills the rest. ### Liftosaur/Liftoscript patterns worth copying [engineering-fact]
Program = text DSL: 'Exercise / sets x reps / weight / @RPE / timer / progress: ... / update: ...'. Key patterns: (a) split 'progress' (runs after workout, between sessions) vs 'update' (runs during workout after each set, setIndex 0 = before first set) -> maps to our session.completed rules vs inSessionRules; (b) per-exercise state vars with defaults custom(attempt: 0, increment: 5lb), user-prompted state (name+), cross-exercise state via tags; (c) built-ins lp(inc, attempts, ..., dec, decAttempts), dp(inc, minReps, maxReps), sum(repsThreshold, inc); (d) set variations '5x3 / 6x2 / 10x1' switched by setVariationIndex (GZCLP-style stage ladder) and exercise variations 'Split Squat | Bulgarian | Pistol' via exerciseVariationIndex = progression ladders -> our B variant 6x2->ladder123 and assistance ladder machine pin -> fingers; (e) addressing weights[week:day:setvariation:set] with wildcards; (f) reuse '...Bench Press[2:1]' and templates 'used: none' -> our 'extends/replace/override'; (g) assisted/weighted BW handled by update script 'weights = bodyweight - originalWeights[ns]' -> proof that assisted/weighted bodyweight must be first-class types, not hacks; (h) functions roundWeight, increment/decrement (equipment-aware), calculate1RM, rpeMultiplier; (i) comparisons on arrays implicitly mean 'all' (completedReps >= reps) - convenient but hides intent; we make all()/any() explicit; (j) imperative statements/loops allowed -> harder to statically validate; we keep expressions pure and actions declarative.
SRC: https://www.liftosaur.com/doc/liftoscript

### wger dynamic routines (open source) patterns [engineering-fact]
Routine -> Day(order, need_logs_to_advance, is_rest) -> Slot (superset if >1 entry) -> SlotEntry(exercise, weight_rounding, repetition_rounding). Per-field config tables (weight, max-weight, reps, sets, rir, rest) with rows {iteration, value, operation r|+|-, step abs|percent, repeat, requirements{rules:[weight,repetitions,rir,rest]}}; value at iteration n = stacked result of preceding rows; requirement rule applies only if all listed fields were met in >=1 log of previous iteration. WorkoutLog stores actual AND originally prescribed target values. fit_in_week pads to weekday. Take: need_logs_to_advance (completion-driven advance = missed-week rule), logs keep target+actual, declarative step ops, rounding per entry.

### Expression/rule language options [engineering-fact]
CEL: non-Turing-complete, side-effect free, guaranteed termination, deterministic ('a CEL expression will deterministically evaluate to either a value or an error'), cost estimation, macros all/exists/map/filter; JVM impl cel-java (protobuf dependency, heavy for Android). JSON-Logic: rules as JSON {op:[args]}, no eval, no setters/loops/functions, extensible ops; verbose, unreadable for long progression logic, no units. json-rules-engine: conditions all/any/not over facts; 'Rules with the same priority are run in parallel' -> ordering nondeterminism hazard; we need total order. Conclusion: custom FitExpr (Pratt parser, ~700 LOC) with typed units + decimal math gives readability (Claude Code reviews), static validation and determinism; store infix strings, compile to cached AST.
SRC: https://github.com/google/cel-spec/blob/master/doc/langdef.md | https://jsonlogic.com/ | https://github.com/CacheControl/json-rules-engine/blob/master/docs/rules.md

### OAP e1RM likely overestimated [moderate]
Multiplier 3RM->1RM differs by formula (computed for r=3): Brzycki 36/(37-3)=1.059 -> +38.6; Lander 1.072 -> +39.9; O'Conner 1.075 -> +40.2; Wathan 1.090 -> +41.8; Epley 1+3/30=1.10 -> +42.8 (used); Lombardi 3^0.10=1.116 -> +44.5; Mayhew 1.140 -> +46.9 (all at BW 70.7, 3RM +32.5, total 103.2 kg). User's own data: nulmeting measured 1RM total 103 / 3RM total 97 = 1.062. Program slope 2.17 kg/rep = (103.2-70.7)/(18-3), i.e. linear line between BW x18 and +32.5 x3 -> linear extrapolation to 1 rep = +36.8. Anchored Epley T(r)=T1*k/(k+r-1) fitted to (3 reps 103.2, 18 reps 70.7) gives k=30.6 -> x1.065 -> +39.2; fitted to slope 2.17 at anchor (90.7 kg, 5 reps): k=90.7/2.17-4=37.8 -> x1.053 -> +38.0. Artifact itself says user's rep curve is flatter than tables, which implies LOWER multiplier, contradicting x1.10. => true single probably +37..+40, so phase-1 gate (+44) is ~4-7 kg away, threshold +46 ~6-9 kg away (still within 6-12 month timeline). Gates must use a measured single or personal-curve e1RM; anchored loads (A/B/C) are unaffected because they derive from the measured 20 kg 4x5 anchor; negatives at 47.5 = 118.2 kg total = 104% (Epley T1) or ~108% (personal T1) of 1RM - acceptable eccentric overload. Individual variability is large: Nuzzo 2024 meta-regression (7289 people, 269 studies) between-person SD 2.51 reps at 80% 1RM, 4.36 at 60% -> per-user calibration needed.

### OAP threshold sanity [expert-opinion]
Willoughby (The Super Athletes): one-arm chin = two-arm chin + 2/3 BW -> +47.1 kg at 70.7 kg. Pavel Tsatsouline (StrongFirst forum): at 1/2 BW added start single-arm drills, keep going to 2/3 BW. 'Journeyman' (StrongFirst): ideal +70% BW (+49.5 kg) and >=20 strict BW reps before specialized one-arm work, achievable without it. Kavadlo 65-75% (artifact). Artifact's 65% (+46.0) = lowest end of range. Engine should store threshold as ratio x BW (recompute when BW changes), not fixed +46. ### OAP structure sanity (unilateral early, frequency, negatives) [expert-opinion]
Unilateral practice from week 1 in parallel with heavy bilateral strength matches Pavel's advice (single-arm drills from ~1/2 BW). StrongFirst consensus: ~2 one-arm sessions/week sustainable; program has one-arm work in A (heavy) + C (moderate, RIR2) + daily habit bilateral -> OK, max-3 cap fine. Negatives: Journeyman warns negatives expose elbows to torque; two trainees lost elbow pain after replacing negatives with lock-offs; others (Mike E) use eccentrics successfully. Program keeps bilateral weighted negatives (B) + 1 one-arm calibration negative/arm (A), first removed at pain -> reasonable compromise. Isometrics are joint-angle specific; long-muscle-length isometrics transfer better to dynamic performance (Oranchuk 2019) -> top hold (short length) trains lockout only; the hardest part per artifact is first 20 deg from dead hang (long length) -> support re-enabling 'starts from dead hang' (parked) and phase-2 multi-angle holds incl. near-extension.

### Deload / test week design [moderate]
Bosquet et al. 2007 (Med Sci Sports Exerc) taper meta-analysis: 2-wk taper with volume exponentially reduced 41-60%, intensity and frequency maintained = most efficient (mostly endurance data). Pritchard et al. 2018 JSCR: 3.5-5.5 days training cessation after 4-wk blocks improved max-strength expression. Bell et al. 2023 Delphi (Sports Med Open): deload = 'period of reduced training stress designed to mitigate physiological and psychological fatigue, promote recovery, and enhance preparedness'; no universal duration/frequency. Coleman et al. 2024 PeerJ: 1-wk full cessation mid 9-wk program gave no hypertrophy benefit, slightly worse strength. => artifact's '4 build + 1 deload: halve sets, keep load, test on deload Sunday' matches taper evidence (volume -50%, intensity kept). Note test-day battery (3RM and/or 1RM, max reps, hang L/R, top hold L/R, least assist L/R, negatives) is long; order matters; max-reps test last.
SRC: Bosquet L, Montpetit J, Arvisais D, Mujika I 2007 MSSE (via Europe PMC) | Pritchard HJ et al. 2018 JSCR (via Europe PMC) | Bell L et al. 2023 Sports Med Open (via Europe PMC) | Coleman M et al. 2024 PeerJ (via Europe PMC)

### RIR self-report accuracy [moderate]
Halperin et al. 2022 Sports Med meta-analysis (12 studies, 414 participants): people underpredict reps to failure by 0.95 reps on average; accuracy better closer to failure and at heavier loads (<=12 reps). Implication: rules like 'min RIR >= 2' are conservative-biased (OK for safety); log raw RIR, never auto-correct in v1; later per-user bias from occasional AMRAP/test sets.
SRC: Halperin I et al. 2022 Sports Med 'Accuracy in Predicting Repetitions to Task Failure' (via Europe PMC)

### Elbow risk context [weak]
Elbow/forearm = 4th most common climbing injury site (after finger, shoulder, hand); medial epicondylalgia usually FCR/pronator teres tendinopathy; brachialis tendinopathy from repetitive elbow flexion without recovery. Supports artifact's 3 stop-signals (medial ache hours after, crease pain on extension, ulnar tingling), neutral handle for full-extension one-arm hanging, prehab every session, 2-week unilateral ban. Evidence base thin (no OAP-specific studies).

### Schedule feasibility [engineering-fact]
Hard rules: 3 gym sessions/week, >=1 rest day between gym sessions, rest day before B. With C Wed, A Fri, B Sun: Sat blocked (before B), Thu blocked (between C and A), Tue blocked (day before C), Mon blocked (day after Sun B). => no 4th gym day possible in any arrangement of 3 sessions with 1-day gaps + rest-before-B in a 7-day week (3 sessions + 3 gaps + ... uses all 7 days). Push/legs must go as add-ons inside C/A, or the gap rule must apply only to sessions loading pull/grip muscles. Test date arithmetic: 11-10 -> 08-11 = 28 days (4 weeks), later intervals 35 days -> postponing test 1 silently shortened block 2 unless later tests shift (artifact: undecided).

## DESIGN OPTIONS
- Expression language for definitions: [JSON-Logic (data-only, existing libs, verbose, no units) / CEL via cel-java (spec'd, non-Turing, deterministic; heavy protobuf deps on Android, no units) / Custom FitExpr: infix strings -> typed AST, decimal, units, explicit all/any / Liftoscript itself (proven domain DSL; TS impl, imperative, no L/R or assist semantics) / Embedded Lua/JS/Rhino (Turing-complete, sandboxing and determinism problems)] -> Custom FitExpr (strings in definition, compiled + type-checked at publish).. WHY: Readable for Claude Code reviews and the user, statically checkable against declared vars, unit/dimension safety (kg vs lb pins vs seconds), decimal determinism, ~700 LOC; avoids JSON-Logic verbosity and CEL dependency weight; keeps actions declarative (no statements) unlike Liftoscript.
- Where challenge definitions live and how they are authored: [Hardcoded Kotlin/TS per challenge / JSON bundled in app assets / Supabase table (immutable versioned jsonb rows, pg_jsonschema CHECK), authored in repo, synced to device cache / In-app visual editor] -> Repo-authored JSON -> CI validation + golden simulations -> published to Supabase challenge_definitions (slug, semver, sha256, status draft|published|retired); app caches; enrollment pins version.. WHY: User wants data-driven toggles and periodic Claude Code reviews; versioned immutable rows give reproducibility; no app release needed for a new challenge or a tuned rule; editor can come later.
- Enrollment state storage: [Mutable state row updated in place / Event-sourced: append-only events + deterministic fold + cached snapshot] -> Event-sourced with cached state + per-block snapshots.. WHY: Replays under new engine/definition versions (what-if analysis for reviews), complete audit, trivially implements 'return to level of two blocks ago', robust offline (gym) with later sync.
- Rule execution semantics: [Forward-chaining (Rete-like), rules see each other's writes / Priority-ordered sequential writes / Staged single-pass snapshot semantics + first-writer-wins + locks + bounded derived-event cascade] -> Staged snapshot semantics.. WHY: Order-independent conditions (all read pre-state), deterministic total order, guards (grip slip) beat increases without fragile ordering, guaranteed termination; json-rules-engine's 'same priority runs in parallel' is exactly the nondeterminism to avoid.
- Week advancement: [Calendar-driven (week n = date-based) / Completion-driven (advance only if >= N sessions done; else repeat week)] -> Completion-driven with synthesized calendar ticks.. WHY: Directly implements artifact rule 'missed week: no make-up, same weights'; mirrors wger need_logs_to_advance; test dates become block-relative (ask user whether later tests shift).
- e1RM method for OAP: [Keep user rule (BW+3RM)*1.10-BW / Personal anchored-Epley curve with fitted k / Require measured single on every test day] -> Default to user rule (faithful), compute and display personal-curve and linear estimates side by side, add optional measured single on test day; switch default after first test that has both 1RM and 3RM.. WHY: User's own data implies multiplier ~1.053-1.065 (e1RM +38-39) vs 1.10 (+42.8); gate decisions need truth, but silently changing the user's program is worse; anchored loads unaffected either way.
- Calendar access path: [Android CalendarContract (on-device, READ/WRITE_CALENDAR permission, no OAuth; ExtendedProperties not writable by normal apps) / Google Calendar REST via OAuth (extendedProperties.private, privateExtendedProperty filter, syncToken) / Both] -> CalendarContract for read (and write with description marker) unless another agent chooses REST for other reasons; matcher is source-agnostic.. WHY: No OAuth/verification hassle for a personal app, works offline, Google account calendars already synced on phone; marker-in-description works on both paths.
- Load rounding: [Fixed increments (2.5 kg) / Inventory-based achievable set (plates, dumbbells on belt) with explicit down/up/nearest] -> Inventory-based.. WHY: Reproduces artifact choices exactly (22.5, 27.5, 47.5 = 20+20+5+2.5) and generalizes to cable stacks/dumbbells; rounding direction is part of each rule (negatives round down).
- Phase 2/3 content: [Encode only phase 1 now, add later via new definition version / Encode full skeleton now, tagged P, refine before gate 1 can pass] -> Skeleton now (tagged P), refine with user before first realistic gate pass (likely > 2 blocks away).. WHY: Engine and UI must support phase transitions from day one; content can be versioned later without app release.
- Assistance progression in session A: [Artifact: -5 lb every week unconditionally / Gated: -5 lb only if all 5x3/arm completed; +5 lb after 2 consecutive fails / Autoregulated by RIR] -> Gated (param gatePinDecreaseA=true, user can switch off).. ## RISKS
- e1RM overestimate: Epley 1.10 at 3RM is near the top of published multipliers; user's own data implies ~1.053-1.065 -> true single likely +37..+40 kg, not +42.8. Gates could look closer than they are; negatives prescribed from it are still within normal eccentric overload (~104-108% 1RM) but user expectations/timeline may be off.
- Unconditional weekly -5 lb pin in A (+4.9%/wk one-arm load) likely outruns adaptation -> failed reps, torso rotation, compensation through supinated elbow -> medial elbow/biceps tendon load.
- Supinated one-arm work + weighted negatives = main elbow risk; app must make pain reporting and readiness check fast, otherwise users skip it and safety rules never fire.
- Assisted machine calibration (offset 6.5 kg '6-7 kg', lever ratio assumed 1.0) uncertain and may differ per Basic-Fit machine/location; comparisons across machines invalid -> log machine id.
- Test day too long/fatiguing (strength + max reps + hangs + holds + least assist + negatives) -> later tests underestimate; order matters (max reps must be last).
- Gate criteria are coach heuristics (no research); app must present them as such and allow param changes, not as hard science.
- Regex calendar matching brittle (Dutch titles, em dash, diacritics, user renames) -> wrong session type -> wrong prescription; mitigated by normalization, marker, manual pin, confirmation when score < 0.8.
- Rule interactions: test recalc, progression and injury restore all write the same vars; without strict staging/locks results would depend on order; also definition upgrades mid-challenge can corrupt state without explicit migrations.
- Week processing relies on ticks; if the app is not opened for weeks, catch-up must be idempotent and ordered; DST change 2026-10-25 can break 24 h windows if computed in local wall time.
- Logging burden in gym (L/R x sets x RIR x flags x seconds) -> incomplete data -> rules evaluate on missing values; need prefilled targets, one-tap confirm, auto-timed holds, sensible defaults for missing RIR (treat as unknown -> no increase).
- Faithfulness vs improvement: P-tagged rules could silently change the user's program; must be opt-in and visible.
- Test date drift: block-relative scheduling shifts all future test dates after any postponement (artifact table currently assumes fixed dates with a 4-week block 2).
- Bodyweight changes alter threshold (ratio x BW) and effective loads; stale BW (no weigh-in) skews e1RM and gates -> require weigh-in on test day and prompt weekly.
- Shared Supabase project with chess app: health/training data needs strict RLS and a separate schema; challenge definitions table is global (read-only to users).
- Over-generalizing the schema around OAP; keep v1 minimal and evolve via schema versions with migration tooling.
